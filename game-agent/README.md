# 星港守卫：一周本地模型实验

- 试玩：https://game.doufei.eu.org/
- 进度、截图、反馈及暂停：https://lab.doufei.eu.org/
- 模型：OCI 上已部署的 Qwen3.6-35B-A3B UD-Q3_K_M，仅使用本地推理，不配置付费模型回退。

复用 Docker、Caddy 和 Pi 1.3.0。游戏用 Canvas 2D 和 ES Modules，不依赖外部素材或 CDN。Phaser 适合更复杂的场景管理；本实验的核心是让 16K 上下文的小模型分轮修改少量代码，先用浏览器已有的 Canvas API。

## 一轮的边界

1. 从当前已发布清单指定的 Git 提交导出候选。任务、候选路径、基线提交、错误、代码/基础设施失败次数和下次重试时间持久化到 `checkpoint.json`，进程重启继续原任务。
2. Pi 在内部 Docker 网络中调用 llama.cpp。一轮生成总预算 30 分钟，固定功能最多分三个阶段，每阶段独立上下文、8 次模型回合、12 次文件工具调用。固定功能每阶段只开放一个源码文件，先修改并测试 core，再实现页面或渲染；普通自主审查先在少量源码文件中完成实现并通过既有完整回归，再用独立上下文只写验收声明；验收阶段源码只读，不允许为了迎合声明继续改游戏。将当前内容直接放入提示词，最多额外读取两次；已有源码必须使用小范围 edit，禁止 write 覆盖和大段删除，并逐块检查 Pi 1.3 的 `edits[]` 批量参数。关闭 Pi 内部自动重试，阶段预算跨内部 agent_start 累计。只开放 read/edit/write，没有 shell、SSH、GitHub 或 Docker 管理权限。模型和 Pi 使用真实 16K 上下文，摘要保留 6144 tokens、近期内容 2048 tokens，原始密钥只读挂载；guard 从受信任目录只读挂载。
3. 正常阶段须收到 `agent_end`、最终助手消息 `stopReason=stop`，且至少一次 edit/write 工具成功。JSON 模式进程退出码 0 不足以证明完成。受信任 guard 明确报告回合/工具预算耗尽时，若已有成功写入且本阶段文件确实变化，可以恢复候选并执行同一套边界检查、阶段回归、浏览器验收和新旧差异证明；通过后才允许继续或发布。恢复阶段单独记录 completion=budget-recovered，发布历史标记 budget_recovered，不冒称模型正常完成。没有成功写入、没有实际变化、接口/基础设施故障、普通输出截断、人工暂停和截止均不能走此路径。
   若阶段最终失败，保留最后一次工具拒绝的具体原因并传入下一次提示词，避免错误反馈丢失。重试明确以当前候选和具体失败断言为准，只做最小修复，保留已有工作部分，不重新实现整项功能。每个阶段独立满足完成条件；核心功能契约未通过时禁止进入页面阶段。三阶段任务的中间操作层也单独执行功能与浏览器验收，未通过时禁止进入渲染阶段；避免操作层错误导致只反复重做末尾渲染文件。已完成阶段、摘要和工具数存入检查点，后续阶段失败后从当前文件继续，候选恢复基线时才重置所有阶段。每个完成的模型阶段记录文件 SHA-256。最终失败按语法文件、固定核心/功能测试定位责任阶段，只废弃该阶段记录；其他字节未变且有完成证据的阶段可复用，仍需重新执行适用验证及最终完整验收。验收声明随当前实现重新生成，不复用旧声明。中间阶段不发布；所有阶段完成后仍须通过整套浏览器回归和旧版本差异证明。波次提示额外验证真实运行至第二波、可见文本、暂停冻结/隐藏、恢复和到期消失。
4. 控制器检查路径、文件大小、私密值和离线约束。测试容器完全断网且没有模型密钥，执行固定规则测试、200 秒实际模拟、桌面键盘、手机触控、暂停/继续、渲染、布局和异常检查。额外用真实 Canvas 直接绘制准备/晚期战斗/暂停状态（包含精英、补给、伤害和护盾），捕获后续场景的渲染异常，并比较前后完整状态，禁止绘制层更改核心状态与计时器。基础规则、功能和浏览器场景使用固定随机种子；补充低/高掉落随机数和既有重叠补给的致死碰撞场景，确保同帧补给不能把已击败的玩家复活，避免偶发失败被误交给渲染层。
5. 每轮还需有 `game/acceptance.json`：1–4 个声明式 core/ui/visual 用例。已有固定功能契约的十二项任务由控制器提供对应的最小声明并记录模型完成摘要，模型只负责源码；普通自主审查由模型在独立验收阶段根据实际源码 diff 提出用例。提示词列全字段和限制，不再放入可照抄的虚构选择器；write 前即时检查 JSON、用例数量、steps 类型、UI 属性和任务 ID，最终仍由受信任的 Python 验证器校验完整场景边界。已通过回归的实现不会因声明格式错误整轮重做。候选必须通过全部既有用例，并至少有一个新用例在已发布基线上失败。仅注释、未加载文件或重复实现不能算有效改进。已接受用例复制到模型不可写的契约清单；后续轮次持续回归。最高战绩还固定检查已存数据、无效/不可用存储、真实得分保存、游戏结束/重开和刷新；敌机、补给、升级、波次、伤害、精英和护盾有独立功能契约；精英额外检查预警倒计时实际结束、预警期免伤/结束后接触伤害、多次命中与死亡奖励、普通敌机继续生成和基于时间的波次不被奖励改写；补充键盘焦点、Escape/P 暂停与恢复、新手说明、后期速度/生成间隔和越界子弹清理检查。
6. 用私有 Git 索引和 `commit-tree` 准备提交，不移动已发布 HEAD。准备完整不可变目录、截图及发布清单，写入 `pending.json`，最后在控制 API 共享锁内复核截止/运行状态并切换指针。进程中断后，指针已切换则补记成功一次，未切换则继续保留旧版和待修候选。
7. HTML 由发布器注入固定版本的资源基址，模块、样式等都从 `/releases/<版本>/game/` 加载。周期内保留所有不可变版本，避免页面请求跨越发布时混用文件；截图也随同一发布指针切换。过期清理不参与发布成功判定。
8. 人工暂停/结束和进程中断不消耗失败次数，也不推进任务；容器退出与暂停发生竞态时仍按控制中断处理。模型未完成、基础设施和代码错误分别统计，但所有失败共同计入回退阈值：核心尚未通过时每三次恢复整个候选；核心已通过时保留前置阶段，每次重试只恢复当前页面文件；普通自主审查的验收阶段失败则保留已通过回归的源码，只重写声明。波次页面只允许两个固定插入点，不能改写已有 HUD 或直接修改核心状态；仅行首缩进不同且片段唯一匹配时对齐编辑锚点，有歧义仍拒绝。每次重试前先检查入口和文件边界，发现损坏立即恢复基线。六次仍未完成则明确记为“重新排队”，先执行后续任务，完成首轮任务表后重新尝试，不能记为已发布。基础设施退避为 4/8/16/32/60 分钟，模型未完成和代码错误最多等待 15 分钟；重启不会清零。连续三次被 guard 拒绝的工具调用提前结束本阶段，避免无效读取和写入耗完整个半小时。成功轮次间隔 2 分钟。失败轮次的已完成消息也计入 token 统计；尚未收到 usage 的中断流无法精确计量。

验收格式示例：

```json
{"task":"weapon-upgrade","checks":[{"kind":"core","initial":{"score":100},"steps":1,"path":"level","op":"gt","value":1}]}
```

示例只说明字段格式，具体用例必须对应当前任务。core 从 playing 状态开始，合并 initial，以 1/60 秒执行 steps 次，最多 4000 次；input 支持移动和护盾。UI 使用单个真实元素 ID，phase 为 ready/playing/paused，property 为 text/visible/attribute；attribute 仅支持 aria-label、aria-describedby、tabindex、role、title。比较支持 eq/gt/gte/lt/lte/contains/exists。视觉用例为 `{"kind":"visual","selector":"#arena"}`，在相同随机种子和虚拟时钟下对比画布；后续允许继续改进画面，不固定整幅图的像素。

自动验收证明指定行为与回归条件，不代替对乐趣、平衡和视觉质量的试玩评价。既有版本升级运行器时先补跑固定功能验收，不伪造历史模型轮次为新流程成功。

## 时间、控制与资源

`/srv/game-agent/config.json` 保存一次性的绝对开始和截止时间。截止为开始后 168 小时，进程重启、暂停和恢复都不会延长；截止后保留游戏并停止迭代。除循环内检查外，`starharbor-deadline.timer` 按相同的绝对时间独立停机，Persistent=true 使错过的截止在服务器恢复后补执行。服务设置 Restart=on-failure，服务器重启后从已保存状态继续。用户点“结束任务”后不能从页面恢复。

模型沿用 2 核 / 18 GiB 配额，设置 `--cache-ram 0`，关闭额外跨提示 RAM 缓存，保留活动槽的 KV 前缀复用，避免缓存挤出模型权重而反复读盘；Pi 工作者为 0.5 核 / 768 MiB；测试为 0.75 核 / 1 GiB，开发和测试分阶段执行。发布控制器 256 MiB，控制 API 96 MiB。磁盘剩余小于 12 GiB 时暂停新轮次；候选及日志保留最近 30 轮，试玩发布目录保留整个运行周期的不可变版本，完整已接受源码历史保留在本地 Git。

反馈和暂停需要独立控制密钥 `/srv/game-agent/control/api-key`。浏览器只在当前页面内存中使用密钥，不写 localStorage。反馈内容由下一轮读取，不会修改绝对截止时间。控制 API 独立于游戏页面的 Origin，游戏设置 connect-src 'none'，不能调用任务控制接口。

```text
/opt/starharbor-agent/         # 受信任的运行器、固定测试、控制网页、镜像构建文件
/srv/game-agent/
├── config.json              # 固定截止时间和运行镜像 ID
├── control/                 # 独立密钥与运行/暂停/反馈指令
├── history/                 # 已发布源码的 Git 仓库，不挂载给模型
├── baselines/               # 按提交导出的只读基线
├── checkpoint.json          # 私有恢复检查点
├── contracts.json           # 私有已接受验收用例
├── pending.json             # 发布进行中时的事务记录
├── rounds/                  # 候选、私有 Pi 日志和测试输出
└── public/
    ├── current -> releases/...  # Caddy 使用的当前通过版本
    ├── state.json           # 无密钥的阶段和迭代记录
    └── releases/<版本>/     # game/、截图和不可变发布清单
```

## 运维与验证

运行镜像从固定摘要的 Node 24.22.1 ARM64 镜像构建，npm 依赖由 lock 文件固定。运行器配置保存实际构建 image ID，而不是跟随可变标签。`starharbor-model` 为 internal Docker 网络，只连接模型与临时 Pi 容器；测试使用 network=none。

```sh
python3 -m unittest discover -s game-agent/tests -p '*_test.py' -v
node --test game-agent/tests/guard.test.mjs
sudo systemctl status starharbor-agent starharbor-control --no-pager
sudo journalctl -u starharbor-agent -n 50 --no-pager
sudo systemctl stop starharbor-agent       # 紧急停机；不会删除已发布游戏
sudo systemctl start starharbor-agent      # 未到期且未在页面结束时继续原周期
```

不要在运行时执行 bootstrap.py 覆盖状态或重新设置截止时间。更改受信任的运行器前先暂停任务并做异机加密备份，保留历史、检查点、契约与控制文件。`control/decision.lock` 应由 game-control 用户拥有、权限 0600，供控制 API 与 root 发布器共同加锁。密钥、候选日志、运行时配置和数据不提交到公开仓库；本仓库保存可重建的基线与运行器。
